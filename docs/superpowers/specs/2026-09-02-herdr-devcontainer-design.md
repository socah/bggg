# Herdr-Enabled Development Container

## Status

Approved design for implementation.

## Goal

Make the repository's development container provision a usable Herdr-based
OpenCode environment, including the Herdr agent skill, OpenCode integration,
the `herdr-agent-quota` plugin, optional Linux host desktop notifications, and
OpenCode session titles in Herdr's Agents pane.

The container must continue to support the existing Node, Docker Compose, and
worktree development workflows. Host-side Herdr remains a supported
alternative and must not be modified by container setup.

## Decisions

### Runtime and provisioning

Use a Node 22-based Dev Container because the repository requires Node
`>=22.22.3`. Keep Docker-in-Docker so the existing workflow can run Docker
Compose from inside the container.

Provision user-facing tools with an idempotent `setup-herdr.sh` run by
`postCreateCommand`, rather than baking user configuration into the image:

- Install the latest stable Herdr binary when it is missing.
- Install the OpenCode CLI when it is missing.
- Install the global `herdr` agent skill with
  `npx skills add herdrdev/herdr --skill herdr -g`.
- Install Herdr's OpenCode integration with
  `herdr integration install opencode`.
- Install `levi-qiao/herdr-agent-quota` from its GitHub repository, following
  its documented installer and enabling the OpenCode collector.

The Herdr plugin source is kept in a user-owned cache directory and follows
the repository's default branch, matching the requested latest-stable
behavior. Plugin configuration and Herdr state remain under the container
user's home directory. The setup does not automatically launch the Herdr TUI;
the developer starts `herdr` interactively.

### OpenCode and Herdr configuration

The checked-in repository `opencode.json` remains unchanged except if a
strictly necessary compatibility adjustment is discovered during
implementation. Herdr's OpenCode integration is installed in the user
configuration directory, so it composes with the existing `superpowers`
plugin.

Setup owns a small, documented portion of Herdr's user config:

```toml
[ui.toast]
delivery = "system"

[ui.sidebar.agents]
rows_by_agent = { opencode = [["state_icon", "agent"], ["terminal_title_stripped"]] }
```

The actual implementation must merge these values without replacing
unrelated existing Herdr settings. `terminal_title_stripped` is used because
Herdr's OpenCode integration and terminal title handling expose the current
OpenCode-generated title through this supported sidebar token. If no title is
available, the second row naturally disappears.

### Linux host notifications

The Dev Container binds the Linux host's session D-Bus socket to a neutral
path such as `/tmp/host-dbus-bus` and sets `DBUS_SESSION_BUS_ADDRESS` to that
path. Herdr uses `system` toast delivery, allowing notifications generated by
the container's Herdr server to reach the host desktop.

The setup checks that the mounted path is actually a socket before relying on
it. If the socket is absent, setup emits a warning and keeps Herdr usable
without host desktop notifications. The D-Bus mount is limited to the
session bus needed for notifications; it does not mount the host Docker
socket.

The primary supported container path is Linux. A developer may instead run
Herdr and OpenCode on the host; the repository documentation will explain
that mode and will not attempt to make host Herdr observe container process
IDs.

### Lifecycle and error policy

Provisioning runs in this order:

1. Check and install required command-line tools.
2. Install or repair the global Herdr skill.
3. Install or repair the OpenCode Herdr integration.
4. Clone/update and install the quota plugin for OpenCode.
5. Merge the owned Herdr notification and sidebar settings.
6. Report the installed components and any optional notification limitation.

Each operation is safe to repeat. Existing user credentials, unrelated
OpenCode plugins, and unrelated Herdr config are preserved. Required tool or
plugin installation failures exit nonzero so `postCreateCommand` reports an
incomplete environment. Missing D-Bus or optional host notification support
is a warning, not a provisioning failure. A documented manual repair command
reruns the same setup after an external tool update.

## Components

Expected repository changes:

- `.devcontainer/devcontainer.json` with the Node 22 image, Docker feature,
  Linux D-Bus mount, port declarations compatible with the existing dev
  workflow, and `postCreateCommand`.
- `.devcontainer/setup-herdr.sh` containing idempotent tool, skill,
  integration, plugin, and Herdr-config setup.
- Shell tests for setup behavior with all network and external commands
  stubbed.
- Focused documentation describing container and host Herdr modes,
  notification prerequisites, repair commands, and verification commands.

The implementation must account for the repository's existing worktree port
allocation rather than silently assuming only fixed ports. Production Compose,
application business logic, and unrelated frontend code remain out of scope.

## Testing

Automated tests will verify:

- Missing tools are installed through the expected official commands.
- Existing tools are not reinstalled unnecessarily.
- Skill, integration, and plugin setup is idempotent.
- The quota plugin installer receives the OpenCode-only configuration.
- Unrelated Herdr config survives the merge.
- The OpenCode title row and system notification setting are generated.
- A missing D-Bus socket produces a warning without failure.
- An available D-Bus socket enables host-notification configuration.
- Required installation failures return nonzero.

Verification will include shell syntax checks, all existing shell tests, the
new setup tests, Dev Container JSON validation, and a real
`devcontainer up --no-session` smoke test when Docker and the Dev Container
CLI are available. Manual runtime checks will confirm Herdr integration and
plugin status, global skill installation, OpenCode title display, and a host
desktop notification when D-Bus forwarding is available.

## Acceptance Criteria

- Reopening the repository in its Dev Container provisions Herdr, OpenCode,
  the global Herdr skill, the OpenCode integration, and
  `herdr-agent-quota`.
- Re-running provisioning is safe and does not duplicate or destroy user
  configuration.
- OpenCode panes report native Herdr lifecycle/session state.
- OpenCode's generated session title appears beneath `opencode` in the
  Herdr Agents pane.
- Linux host system notifications work when the host session D-Bus socket is
  available, and missing D-Bus support is clearly reported without breaking
  the container.
- Developers can still choose a host-side Herdr runtime.
- Existing development workflows and tests remain functional.
